## Context

当前仓库已经完成顶层结构优化（归档 + daily + 章节目录保留），但 daily 历史内容尚未成体系。目标是利用 GitHub 全历史提交，建立可追溯的 `day01..dayNN` 学习时间线，并与章节代码路径形成回链。该变更属于文档与学习索引层，不应影响章节代码本体。

## Goals / Non-Goals

**Goals:**
- 从 GitHub 全历史提取稳定时间线并按日期聚合。
- 建立 day 编号规则（从最早日期递增）与日期映射。
- 批量生成高完成度 day 初稿，统一模板字段与章节回链。
- 对低信息量日期使用统一策略（合并或占位）。
- 提供可验证规则：编号连续、路径有效、模板完整。

**Non-Goals:**
- 不修改章节目录内代码和 notebook 内容。
- 不重构归档目录内容。
- 不在本次变更中实现高级自动摘要模型流程（先以可控规则生成）。

## Decisions

1. **历史来源优先级：GitHub 提交记录优先，目录日期作为辅证**
   - 决策：以 `gh` 提交历史为主生成时间线，归档日期目录用于交叉校验。
   - 原因：提交历史是线性可验证来源，覆盖“何时有有效学习产出”。
   - 备选：仅按归档目录生成；可能遗漏无日期目录但有提交的学习日。

2. **day 编号从最早日期递增且保持稳定**
   - 决策：`day01` 对应历史最早有效日期，之后连续递增。
   - 原因：便于长期扩展与固定引用。
   - 备选：从最新日期递减编号；会随新增历史回填导致编号漂移。

3. **低信息量日期采用“占位优先、必要时合并”**
   - 决策：默认每个有效日期生成一篇 day；若当天提交仅为无学习语义的元变更，可在文档中标记“轻量日”。
   - 原因：保持时间线连续性，避免过度主观合并。
   - 备选：强制合并低信息日；可读性提升但会损失时间线精确度。

4. **模板字段强约束**
   - 决策：每篇 day 必须包含章节字段、关键路径、至少一个问题/坑位（可为“暂无明显错误，记录风险点”）。
   - 原因：保证“可复盘”而非流水账。
   - 备选：弱约束自由写；完成度不稳定。

## Risks / Trade-offs

- [提交信息不足导致内容空洞] → 结合文件路径与目录上下文补充结构化占位，后续人工微调。
- [一天多次提交信息重复] → 聚合到单篇 day，按时间顺序压缩摘要。
- [路径回链失效] → 生成后做路径存在性校验并输出异常清单。
- [编号调整成本] → 固化“最早日期起编号”规则，避免后续重排。
